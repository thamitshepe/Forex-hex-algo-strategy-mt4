# Demo Test Plan

A 30-day protocol for deciding whether HEX-FVG-Breaker earns a small live
account. It exists because the hard part of building a trading system is not
writing it, it is refusing to kid yourself about whether it works.

Read this before you change any setting, and change **one** setting per test
window. If you change three things at once you have learned nothing.

If the EA is not yet compiled, attached and logging, start with **`FIRST-RUN.md`**
— the install-to-first-notification checklist. This file begins where that ends.

---

## 1. What you are actually testing

You are testing three separate things, and a failure in one is not a failure of
the others:

| Question | Evidence | If it fails |
|---|---|---|
| Does the logic find setups? | signals.csv rows per day | tune detection, or accept it is too selective |
| Do those setups make money after costs? | trades.csv, R-based expectancy | the edge is not real, stop |
| Can a $100 account survive it? | equity.csv drawdown, margin rejections | fix sizing, not the logic |

Most people skip the first row, panic at the third, and never answer the second.

---

## 2. Setup

1. **Account:** $100 demo, live-size. Not $10,000, not $100,000. Margin and
   spread behave completely differently at $100, and that is what you test here.
2. **Chart:** XAUUSD **M15**, one chart only.
3. **Preset:** load `MQL4/Presets/100usd-demo.set` (generated by
   `Tools/make_presets.py`).
4. **VPS or a machine that stays on.** A laptop that sleeps is not a test. If you
   want it off your machine entirely, `DEPLOY.md` builds the same setup as a
   container on a Linux VPS (GHCR + Dokploy), including the two switches a
   headless terminal cannot set for itself.
5. **AutoTrading on**, and confirm the EA shows the smiley face.

Then write down, before day one, what you expect. If you did not write it down,
you will reshape your expectations to fit the results.

---

## 3. Windows

Run each window for **at least 10 trading days or 20 closed trades**, whichever
comes later. Fewer than 20 trades is noise; a 60/40 win rate on 10 trades means
nothing.

| Window | Preset | Question |
|---|---|---|
| A (start here) | `100usd-demo` | baseline: does it work as shipped? |
| B | `100usd-shadow` | what is being missed, and why |
| C | `structure-only` | is the EMA stack helping or hurting? |
| D | `trigger-entry` | limit vs trigger entry |
| E (optional) | `london-ny-window` | is spread eating the edge? |

Run A first and finish it. Do not switch presets mid-window.

---

## 4. Daily (2 minutes)

    python3 Tools/hex_report.py

Check only these:

- **trades per day** - close to zero? The filters are too tight; read the
  rejection table before touching anything.
- **margin / spread rejections** - if these dominate, the account is too small
  or the broker's gold spread is too wide for this strategy. That is a real
  finding, not a bug.
- **equity curve** - any single day worse than 5% means a kill switch should
  have fired. If it did not, that is the bug worth fixing.

Do not adjust anything on daily data. Daily reads catch breakage, nothing more.

---

## 5. Go / No-Go

These are the rules `Tools/hex_report.py` applies (function `go_no_go()`). The
report prints the verdict; this is what it means.

**Fewer than 20 closed trades: INCONCLUSIVE.** Run longer. Conclude nothing, in
either direction.

All four must pass:

| Test | Threshold | Why |
|---|---|---|
| Expectancy | **> 0 R** | below zero it loses money at any win rate |
| Profit factor | **>= 1.15** | below about 1.15, real costs and slippage erase it |
| Equity drawdown | **< 12%** | a $100 account down 12% is hard to compound back |
| Drawdown in R | **< 10 R** | catches a system that needs only a bad streak to fail |

**Spread cost above 0.12 R per trade is a warning, not a fail.** On gold with a
$100 account it is usually the single biggest reason a good idea stops working,
and the fix is a different broker or account type, not a different strategy.

What to do with each verdict:

- **PASS** - do not scale up yet. Repeat window A on a second demo account.
  Only then consider a real $100.
- **FAIL on expectancy or profit factor** - the edge is not there. Do not tune
  your way to a pass on 25 trades; you have simply found the window that worked.
- **FAIL on drawdown** - the logic may be fine and the sizing wrong. Check
  whether losses cluster (same direction, same hour) before touching the logic.
- **INCONCLUSIVE** - almost always too few trades. The rejection table usually
  names the exact filter that is starving the system.


---

## 6. Rules that keep the test honest

1. **One change per window.** Otherwise the result is unattributable.
2. **Never retune on a window you already judged.** A new parameter means a new
   20-trade window, starting now.
3. **Do not delete a losing trade as "bad luck".** The stop was hit; that is the
   system working.
4. **Commit the preset files with the dates you ran them.** A month from now you
   will not remember which settings produced which curve.
5. **The report is R-based on purpose.** Dollar curves flatter you at $100 and
   punish you at $10,000; R asks the same question at every size.
6. **If you feel the urge to intervene, write down why.** If the same reason
   appears three times it is a design problem to fix in code, not a trade to
   override.

## 7. Reproducing decisions offline

The EA cannot be unit tested (MQL4 has no test runner), so
`Tools/simulate_logic.py` is the executable specification of the same rules:

    python3 Tools/simulate_logic.py --selftest      # the rules, as assertions
    python3 Tools/simulate_logic.py --demo          # synthetic series
    python3 Tools/simulate_logic.py --csv bars.csv  # your exported M15 data
    python3 Tools/simulate_logic.py --ticks         # intra-bar path sensitivity

Use it to check that a behaviour you saw on the demo is what the logic is
supposed to produce, and to measure how often a setup occurs before spending two
weeks waiting for one. Its fills are idealised - no slippage, commission or
swap - so **treat its frequencies as meaningful and its P&L as indicative
only.** It is not a backtester and does not replace this plan.

One thing it shows straight away: with `RequireFVGConfluence = true`, a lone FVG
is rejected unless a breaker or mitigation block overlaps it. On synthetic
4,000-bar series that gate roughly halves the trade count (71 vs 141 trades on
one seed, 55 vs 136 on another), and the `TREND_BOTH` default cuts it further.
So if your demo produces almost no trades, these two filters - the confluence
requirement and the dual trend confirmation - are where to look first. They are
both working as designed; the question is whether they are too strict for an
M15 gold account that needs enough trades to learn from.

### Does it hold up on real-time updates?

A backtest that reads one closed bar at a time cannot see the thing most likely
to hurt you live: a single bar that prints **both** your stop and your TP1. The
bar records that both prices were touched but never the order they were touched
in, so the outcome of that bar is genuinely unknown to any OHLC backtest, and
the two readings differ by more than a rounding error - bank half at TP1 and
lock breakeven, or be stopped out for the full loss.

`--ticks` answers this without pretending to have a tick feed. It replays the
identical entries twice: once assuming price visits the bar high first, once
assuming the low first. Where the two runs agree, the result does not depend on
tick order. Where they disagree, it does.

    python3 Tools/simulate_logic.py --ticks --bars 4000 --seed 7

On six synthetic 4,000-bar series (349 trades) the answer is reassuring: about
**28% of trades touch at least one ambiguous bar**, so intra-bar order is
constantly in play, but only **7.4% of trades end with a materially different
result**, and the expectancy gap between the two paths is **0.011 R per trade
on average (worst seed 0.022 R)**. Trade frequency, which setups fire and when,
and the sign of the edge are all path-independent.

Read it as: the strategy's edge is not an artefact of favourable intra-bar
assumptions, so live tick handling should not surprise you much. It is not
proof - the real tick sequence is neither of the two paths tested, and slippage
on a partial close is still not modelled. If a future parameter change pushes
the spread above roughly 0.15 R, the configuration has become dependent on luck
inside the bar and needs a real tick-feed test before going live.

The same ambiguity is why `MinHoldBars` is measured from **fill time, not
placement time**. A limit order that rests four bars before filling is not a
four-bar-old trade; it is a brand-new one. The EA starts that clock when the
pending becomes a position, which is also when the "FILLED" notification fires.

## 8. Notifications

`NotifyUrl` pushes a message to a phone at every decision you would otherwise
have to sit and watch for: signal, order placed, limit filled, TP1 banked,
position closed with its R multiple, and kill switch.

MT4 cannot speak to WhatsApp directly, so the EA posts to an HTTP endpoint that
forwards text into a chat. The least friction is **ntfy.sh**: install the app,
pick a private topic name, set

    NotifyUrl = https://ntfy.sh/your-private-topic

No account, no key, messages appear on the phone in a second. Pushover and a
self-hosted Telegram bridge work too; `NotifyFormat` covers form-encoded, plain
body, JSON and GET.

Three things to know before you turn it on:

- **You must whitelist the address.** Tools → Options → Expert Advisors → "Allow
  WebRequest for the following URLs", add `https://ntfy.sh`. Without it every
  send fails, and the dashboard line `Push : 0 sent, 1 failed (...)` will say so.
- **`NotifyTestOnInit` sends a hello at startup.** Do not skip this: it proves
  the plumbing on day one instead of on the first losing trade.
- **Notifications are disabled in the Strategy Tester**, which cannot make HTTP
  requests. Every message is still written to `notify.csv` with status
  `OK / FAIL / DROPPED / TESTMODE`, so "the EA had nothing to report" stays
  distinguishable from "the message was lost" - and a log replay can be audited
  against what you were told.

Expect a message every time the EA acts, throttled so a frantic market cannot
flood the phone: identical text is suppressed for `NotifyMinMinutes` (default 2)
and the total is capped at `NotifyMaxPerHour` (default 30). Set
`NotifyOnTp1 = false` unless you want a ping on every partial close. With the
trade frequency in section 7, a normal day is a handful of messages, not dozens.

One caveat worth stating plainly: `WebRequest` blocks the EA until the request
returns, so a slow endpoint stalls the tick loop. `NotifyTimeoutMs` (default
3000) bounds that, and nothing is retried - a missed notification is a
documentation gap, never a trading risk.
